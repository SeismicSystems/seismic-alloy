# Seismic-Alloy

> **Note**: This document was generated by Claude.

## Overview

Seismic-Alloy is a Rust toolkit that extends [Alloy](https://github.com/alloy-rs/alloy) to support the Seismic network. Seismic is an EVM-compatible blockchain that allows smart contracts to manage shielded state. This library provides the transaction types, network abstractions, and provider implementations necessary to interact with Seismic networks.

**Repository**: https://github.com/SeismicSystems/seismic-alloy

## Core Concept

Seismic introduces the Seismic transaction, where calldata is encrypted using ECDH + AEAD before submission. This calldata can only be decrypted by nodes that have the network's secret key

Key characteristics:
- Supports all standard Ethereum transaction types (Legacy, EIP-2930, EIP-1559, EIP-4844, EIP-7702)
- Adds a custom Seismic transaction type (type ID `74`) with encryption metadata
- Encryption metadata includes: public key, nonce, block hash, and expiration

## Architecture

This is a Cargo workspace with six crates:

```
crates/
├── consensus/      # Transaction types, receipts, validation
├── network/        # Network abstractions (For seismic-anvil & seismic-reth)
├── provider/       # Blockchain interaction layer
├── rpc-types/      # RPC request/response types, genesis
├── genesis/        # Genesis file definitions
└── prelude/        # Convenience re-exports
```

**Dependency chain**: `consensus` → `network` → `provider`

### consensus

**This is where the core Seismic transaction type lives**

- `crates/consensus/src/transaction/seismic.rs` - `TxSeismic` type and `TxSeismicElements` (encryption metadata)
- `crates/consensus/src/transaction/envelope.rs` - `SeismicTxEnvelope` supporting Seismic transactions
- `crates/consensus/src/transaction/typed.rs` - `SeismicTypedTransaction` union type

The `TxSeismic` struct is a standard transaction type (similar to Legacy, EIP-1559, etc.) with fields like `chain_id`, `nonce`, `gas_price`, `gas_limit`, `to`, `value`, and `input`. It includes an additional `seismic_elements` field of type `TxSeismicElements` that gets flattened during serialization.

**Important**: Seismic transactions use the same gas parameters as legacy transactions (`gas_price` and `gas_limit`), not the EIP-1559 style gas parameters.

```rust
pub struct TxSeismicElements {
    pub encryption_pubkey: PublicKey,
    pub encryption_nonce: U96,
    pub message_version: u8,
    pub recent_block_hash: B256,
    pub expires_at_block: u64,
    pub signed_read: bool,
}
```

### network

Provides the `SeismicNetwork` trait and two concrete implementations:

- `crates/network/src/seismic_network.rs` - Core trait defining network-specific behavior
- `crates/network/src/foundry/mod.rs` - `SeismicFoundry` for Seismic Anvil (sanvil) testing
- `crates/network/src/reth/mod.rs` - `SeismicReth` for Seismic's fork of Reth

The `SeismicNetwork` trait abstracts over differences between test and production environments. Key methods:
- `set_seismic_elements()` / `get_seismic_elements()` - Manage encryption metadata
- `input_encryption()` / `input_decryption()` - Handle encryption/decryption operations
- `sign_seismic_transaction_with_wallet()` - Sign transactions with proper type handling

### provider

Implements blockchain interaction with Seismic-specific extensions:

- `crates/provider/src/builder.rs` - `SeismicProviderBuilder`, `SeismicSignedProvider`, and `SeismicUnsignedProvider`
- `crates/provider/src/traits.rs` - `SeismicProviderExt` (base) and `SignedProviderExt` (encrypted ops)
- `crates/provider/src/decrypt.rs` - `ResponseDecryptProvider` (response decryption layer)
- `crates/provider/src/call_ext.rs` - `SeismicCallExt` and `ShieldedCallExt` (contract call builder extensions)
- `crates/provider/src/security_params.rs` - `SecurityParams` for per-call encryption overrides

The provider layer handles:
- Fetching public keys for encryption
- Encrypting transaction inputs before submission
- Decrypting responses via `ResponseDecryptProvider`
- Conditional signing based on transaction type
- Standard Alloy provider functionality (eth_call, send transaction, logs, etc.)
- Per-call security parameter overrides via `SecurityParams` and `_with` method variants

### rpc-types

Contains RPC-specific types:

- `crates/rpc-types/src/genesis.rs` - Genesis configuration with Seismic hardfork info
- `crates/rpc-types/src/receipt.rs` - `SeismicTransactionReceipt`
- `crates/rpc-types/src/request.rs` - RPC request types
- `crates/rpc-types/src/simblock.rs` - Block simulation types

The genesis format supports `genesis_private_state` for defining encrypted state at chain initialization.

## Key Design Decisions

### Transaction Type System

Seismic transaction type ID is `74` (0x4A). The `SeismicTypedTransaction` enum (in `crates/consensus/src/transaction/typed.rs`) supports all standard Ethereum types (Legacy, EIP-2930, EIP-1559, EIP-4844, EIP-7702) plus the custom Seismic variant.

The Seismic transaction type is like any other Ethereum transaction type but with additional encryption-related fields grouped in `TxSeismicElements`. These fields are flattened when serialized, so they appear at the same level as other transaction fields.

### Network Abstraction Pattern

The `SeismicNetwork` trait allows the same provider code to work with both Seismic Anvil (sanvil for testing) and Seismic Reth (production) without conditional compilation or runtime checks. Network-specific behavior is encapsulated in `SeismicFoundry` and `SeismicReth` implementations.

**Why this pattern**: Testing requires different wallet behavior and transaction building than production. The trait abstraction keeps provider logic clean while allowing network-specific customization.

### Provider Extension Pattern

Rather than fork Alloy's provider system, two extension traits (in `crates/provider/src/traits.rs`) extend it:

- `SeismicProviderExt` — base trait for all Seismic providers (signed and unsigned). Provides `transparent_call`, `transparent_send`, and `get_tee_pubkey`.
- `SignedProviderExt` — sealed trait for signed providers only. Provides `seismic_call`, `seismic_send`, `seismic_call_raw`, `eip712_send`, and `_with` variants that accept `SecurityParams`.

For contract-level calls, `SeismicCallExt` and `ShieldedCallExt` (in `crates/provider/src/call_ext.rs`) add `.seismic()`, `.call()`, `.send()`, `.with_params()`, `.expires_at()`, and `.eip712()` to alloy's `SolCallBuilder`.

This maintains compatibility with Alloy's ecosystem while adding encrypted call functionality.

### Encryption Metadata Design

`TxSeismicElements` bundles all data needed for transaction validation:
- **encryption_pubkey**: Public key for encryption (secp256k1, compressed, 33 bytes)
- **encryption_nonce**: AEAD nonce (12 bytes)
- **block_hash**: Prevents replay across forks
- **expiration**: Block number after which transaction is invalid

This prevents replay attacks and ensures transactions are only valid for a specific chain state.

### Custom Forks

The project depends on custom forks of several upstream libraries:

- **seismic-enclave**: Enclave integration for ECDH encryption/decryption (pinned to specific commit)
- **seismic-alloy-core**: Custom Alloy primitives with Seismic ABI support
- **seismic-revm**: Modified REVM for executing Seismic transactions
- **seismic-trie**: Custom Merkle trie implementation

These forks are necessary because Seismic requires modifications to core Ethereum primitives that upstream libraries cannot support. Commits are pinned in `Cargo.toml` patches section.

## Important Patterns

### InputDecryptionElements Trait

The `InputDecryptionElements` trait (defined in `crates/consensus/src/transaction/seismic.rs`) is implemented by `TxSeismicElements` and defines how transaction inputs can be decrypted. This abstraction allows different encryption schemes while keeping the provider layer generic.

### Builder Pattern for Transactions

Transaction builders support fluent interfaces. For contract calls, use `.seismic()` to opt in to encryption, then chain `.call()` or `.send()`. Override encryption defaults with individual setters (`.expires_at()`, `.encryption_nonce()`, `.recent_block_hash()`, `.eip712()`) or bulk override with `.with_params(SecurityParams { ... })`.

For provider-level calls, use `seismic_call` / `seismic_send` (default parameters) or `seismic_call_with` / `seismic_send_with` (custom `SecurityParams`).

### Feature Flags

- `std` - Standard library support
- `serde` - Serialization (required for RPC)
- `kzg` - EIP-4844 blob transaction support
- `arbitrary` - Property testing support
- `alloy-compat` - Alloy compatibility features

Most features are enabled by default. Use `default-features = false` for no-std builds.

### Error Handling

Key error types:
- `InputDecryptionElementsError` - Decryption failures
- `SeismicValidationError` - Transaction validation (expiration, block hash)
- Alloy errors propagate through provider layer

## Gotchas

### Seismic Transaction Type ID

The Seismic transaction type ID is `0x4A` (74 decimal). This is hardcoded and must not change without coordinated chain upgrade.

### Encryption Public Key Format

Encryption public keys are 33-byte compressed secp256k1 points (`FixedBytes<33>`). Do not use 65-byte uncompressed format.

### Self-Hosted CI Runner

The test job requires a self-hosted runner with sanvil installed. Tests will fail in standard GitHub runners. The runner must have `$HOME/.seismic/bin` in PATH.

### Genesis Private State

The `genesis_private_state` field in genesis configs is encrypted. It's used for initializing confidential contracts.

### Alloy Version Pinning

The project is pinned to Alloy 1.1.0. Upgrading requires coordinated updates across seismic-alloy-core and other forks. Do not bump Alloy version without testing all forks.

### Encrypted vs. Standard Transactions

Seismic transactions can wrap any Ethereum transaction type. The inner transaction determines gas semantics, but the outer Seismic envelope adds encryption overhead. When estimating gas, account for both layers.

### Transaction Expiration

Seismic transactions expire after the specified block number. This prevents long-lived pending transactions and reduces mempool spam. Clients must handle expiration errors and potentially resubmit with updated expiration.

## Contributing Patterns

### Focused Changes

Keep PRs focused on a single change. Avoid combining unrelated modifications (e.g., don't add a feature and refactor unrelated code in the same PR).

### Transaction Type Additions

When adding support for new Ethereum transaction types:
1. Add variant to `SeismicTypedTransaction` enum
2. Update `TxSeismic` to support wrapping the new type
3. Implement serialization/deserialization
4. Add builder methods in provider
5. Update tests to cover new type

### Network Implementation

When modifying `SeismicNetwork` trait:
1. Update both `SeismicFoundry` and `SeismicReth` implementations
2. Consider test vs. production environment differences
3. Update provider methods that depend on network behavior
4. Add integration tests with sanvil

### Testing Encrypted Transactions

Use the test utilities in `crates/provider/src/test_utils.rs`. Tests typically spawn a local sanvil instance using Anvil, fetch the encryption public key via `provider.get_tee_pubkey()`, construct a Seismic transaction with proper encryption metadata, and verify decryption works.

### Avoid

- Do not modify vendored dependencies (seismic-enclave, seismic-revm, etc.) directly in this repo
- Do not change the Seismic transaction type ID (0x4A / 74) without chain upgrade coordination
- Do not add dependencies that conflict with Alloy's version requirements
- Do not implement partial features - ensure encryption/decryption pairs are complete
- Do not skip CI checks - all warnings must be resolved
